# 配置生效说明：本地开发 vs Docker 打包

> 目的：把「环境变量 / 默认值 / 本地开发 / Docker 打包」四者与**实际生效配置**的关系彻底讲清楚。
> 结论先行：**本项目有 3 条启动路径，各自读取的配置来源不同；其中 IDE 启动根本不读 `.env`，这是最容易搞混的地方。**

---

## 0. 一句话结论

| 你的启动方式 | 实际生效的模型配置来自 | 改哪里能生效 |
|---|---|---|
| **IDE 里直接 Run** `YuAiCodeMotherApplication` | ⚠️ **`application.yml` 里的默认值** | 改 `src/main/resources/application.yml`，然后 **Rebuild** |
| **`./run-local.sh`** | ✅ **`.env`** | 改 `.env`，重启脚本即可 |
| **`./deploy.sh` / `docker compose up`** | ✅ **`.env`**（经 compose 中转） | 改 `.env` 即可<br>⚠️ 若改的是 `application.yml`，**必须重建镜像** |

**最关键的一句**：**`.env` 对 IDE 启动完全无效**。项目没有引入 dotenv、也没有配 `EnvFile` 插件，Spring Boot 默认不读 `.env`。

---

## 1. 三条启动路径

### 路径 A：IDE 直接 Run（最常用，也最容易误解）

**执行链路：**

```
IDE Run Configuration (YuAiCodeMotherApplication)
  └─ 无任何 Environment variables（已确认 .idea/workspace.xml 中无 <env> 项）
  └─ 无 EnvFile 插件配置
        ↓
Spring Boot 启动，读 classpath 内的 application.yml
        ↓
占位符 ${LLM_CHAT_MODEL:deepseek-flash}
  └─ 找不到环境变量 LLM_CHAT_MODEL
  └─ 落到冒号后面的默认值 → deepseek-flash   ✅ 这就是生效值
```

**证据：**

- `.idea/workspace.xml:193` 的 Spring Boot 运行配置里**没有 `<env>` 节点**：
  ```xml
  <configuration name="YuAiCodeMotherApplication" type="SpringBootApplicationConfigurationType" ...>
    <module name="yu-ai-code-mother" />
    <option name="SPRING_BOOT_MAIN_CLASS" value="com.yupi.yuaicodemother.YuAiCodeMotherApplication" />
    <method v="2"><option name="Make" enabled="true" /></method>
  </configuration>
  ```
- `pom.xml` 中**没有** `spring-dotenv` / `dotenv-java` 依赖
- `application.yml` 中**没有** `spring.config.import`

**结论**：IDE 启动时，**生效的是 `application.yml` 中 `${VAR:默认值}` 的「默认值」**。

> 想让 IDE 也读 `.env`，有两个办法（见 §6）。

---

### 路径 B：`./run-local.sh`（脚本启动）

**执行链路：**

```
run-local.sh
  └─ 逐行解析 .env，对每行 key=value 执行 export     ← 关键
  └─ export SERVER_PORT=8123（若未设置）
  └─ exec mvn spring-boot:run
        ↓
Maven 派生 JVM，继承上面 export 的所有环境变量
        ↓
Spring Boot：环境变量优先级 > jar 内 application.yml
        ↓
${LLM_CHAT_MODEL:deepseek-flash} 被环境变量 LLM_CHAT_MODEL 覆盖 → 生效值 = .env 里的值 ✅
```

**证据**：`run-local.sh:16-33` 手工解析 `.env`（注释里特意说明**不能直接 `source`**，因为 `.env` 里的 `<` `>` `&` 会被 bash 当语法），然后 `export "$key=$value"`。

> ⚠️ 这一步是纯 bash 行为，与 Spring Boot 无关。脚本只在**通过它启动**时才生效。

---

### 路径 C：Docker 打包运行

**执行链路：**

```
./deploy.sh
  └─ cd 到仓库根目录
  └─ docker compose up -d --build
        ↓
① docker compose 自动读取同目录的 .env，做 ${VAR:-default} 插值
        ↓
② docker-compose.yml 的 environment: 把插值结果作为容器环境变量传入
        ↓
③ 容器内 java -jar app.jar（application.yml 已在构建期打进 jar）
        ↓
④ Spring 用容器环境变量替换 ${LLM_*:...} 占位符
        ↓
生效值 = .env 的值 ✅
```

**关键点 ①②：没有 `env_file` 指令**（已确认 `docker-compose.yml` 中不存在）。这意味着：

> **`.env` 里的变量不会自动进入容器**，必须**逐条列在 `docker-compose.yml` 的 `environment:` 段里**才会传进去。

目前列出的 LLM 相关变量（`docker-compose.yml:120-126`）：

```yaml
LLM_API_KEY:          ${LLM_API_KEY:-<Your API Key>}
LLM_BASE_URL:         ${LLM_BASE_URL:-https://api.deepseek.com}
LLM_CHAT_MODEL:       ${LLM_CHAT_MODEL:-deepseek-flash}
LLM_STREAMING_MODEL:  ${LLM_STREAMING_MODEL:-deepseek-flash}
LLM_ROUTING_MODEL:    ${LLM_ROUTING_MODEL:-deepseek-flash}
LLM_ROUTING_BASE_URL: ${LLM_ROUTING_BASE_URL:-https://api.deepseek.com}
LLM_REASONING_EFFORT: ${LLM_REASONING_EFFORT:-low}
```

**关键点 ③**：`docker/backend.Dockerfile` 是**多阶段构建**，`COPY src ./src` + `mvn package` 在镜像里完成，所以：

> **`application.yml` 是在构建镜像时打进 jar 的。改了它，只 `docker compose restart` 不会生效，必须重新 build。**

## 2. 三层默认值：搞清「默认值」到底指哪一层

同一个变量名出现在**三个地方**，每层都有自己的默认值。理解这个就不会再混：

```
第 1 层（最高优先级）
  .env                             ← 你手动填的真实值
      ↓ 没有该变量时
第 2 层：docker-compose.yml 的 ${VAR:-xxx}     ← 【仅 Docker 路径存在】compose 层默认值
      ↓ 没有该变量时
第 3 层：application.yml 的 ${VAR:xxx}         ← Spring 层默认值（打进 jar，随镜像走）
```

以 `LLM_CHAT_MODEL` 举例：

| 层级 | 位置 | 当前值 | 何时生效 |
|---|---|---|---|
| 1 | `.env` | `deepseek-flash` | 用了 `.env` 的路径（`run-local.sh` / Docker） |
| 2 | `docker-compose.yml:122` | `deepseek-flash` | Docker 路径，且 `.env` 里没有这一行 |
| 3 | `application.yml:48` | `deepseek-flash` | IDE 路径，或前两层都没有时 |

> **注意**：`docker-compose.yml` 的 `LLM_API_KEY` 默认值是 `<Your API Key>` 这个占位串——如果 `.env` 里漏了 `LLM_API_KEY`，容器会拿到这个**假 key**，报 401 而不是报"缺少配置"。这是个隐蔽的坑。

### 关于 `application-prod-sample.yml`

它在 `src/main/resources/` 下、会被打进 jar，但 **对当前运行完全没有影响**：

- Spring Boot 只加载 `application-{profile}.yml`，而**当前没有激活任何 profile**（`application.yml` 里没有 `spring.profiles.active`）
- 文件名叫 `-prod-sample`，所以即使激活 `prod` profile 也匹配不上

**它是给人看的模板**，不是运行配置。改它不会影响任何一次启动。

## 3. 改哪里影响哪里（速查表）

| 你想影响 | 改这个文件 | 生效方式 | 注意事项 |
|---|---|---|---|
| **本地 IDE 启动** | `src/main/resources/application.yml` | **Rebuild 项目后重启** | 改 `.env` **无效** |
| **本地 `./run-local.sh`** | `.env` | 重新执行脚本 | 改 yml 默认值也有效（作为兜底） |
| **Docker 里的模型名/key/URL** | `.env` | `docker compose up -d`（**不必 `--build`**） | 变量必须已在 compose 的 `environment:` 里列出 |
| **Docker 里的默认值**（.env 没写的那些） | `docker-compose.yml` 的 `${VAR:-默认}` | `docker compose up -d` | 不必重建镜像 |
| **Docker 里的 Spring 兜底默认值** | `src/main/resources/application.yml` | ⚠️ **必须 `--build` 重建镜像** | 只 restart 无效，因为已打进 jar |
| **三者同时改** | 三处都改 | — | 推荐做法，见 §7 |

### 「重建镜像」vs「重建容器」的区别

```bash
# 只重建容器，复用已有镜像 —— 改 .env / docker-compose.yml 用这个
docker compose up -d

# 重新编译源码、重建镜像 —— 改 application.yml / Java 代码用这个
docker compose up -d --build
```

> `deploy.sh up` 恒等于 `docker compose up -d --build`，**总会重建镜像**。
> 所以只改了 `.env` 却跑 `./deploy.sh`，会白白等一次完整 Maven 构建。
> 想省时间就直接用 `docker compose up -d`。

## 4. 五个容易踩的坑

### 坑 1：改了 `.env`，IDE 启动没变化

**原因**：IDE Run 不加载 `.env`。
**解决**：要么改用 `./run-local.sh`，要么给 IDE 配置环境变量（见 §6）。

### 坑 2：改了 `.env` 里一个新变量，Docker 里却不生效

**原因**：没有 `env_file` 指令，`.env` 只用于 compose 的**插值**；变量没写进 `docker-compose.yml` 的 `environment:`，就不会进容器。
**解决**：在 `docker-compose.yml` 的 `environment:` 里补一行 `新变量: ${新变量:-默认值}`。

### 坑 3：改了 `application.yml`，Docker 里没变化

**原因**：yml 在 `docker build` 时已打进 jar。
**解决**：`docker compose up -d --build`。

### 坑 4：`.env` 漏了 `LLM_API_KEY`，Docker 报 401 而不是报缺配置

**原因**：`docker-compose.yml` 的兜底值是字符串 `<Your API Key>`，会被当成真实 key 传给模型。
**解决**：部署后确认 `docker compose exec backend env | grep LLM_API_KEY` 不是占位串。

### 坑 5：本地 IDE 与 Docker 用不同模型，排查时对不上

**原因**：两条路径的来源不同（ylm 默认值 vs `.env`）。
**解决**：用 §5 的方法确认当前生效值。

## 5. 怎么确认「当前实际生效的是哪个值」

### 方法 1（Docker，最直接）

```bash
docker compose exec backend env | grep ^LLM_
```

看到的就是容器内真实环境变量。**注意**：这只能看到环境变量层，如果某个变量没传进去，这里就看不到——那说明 Spring 会落到 `application.yml` 的默认值。

### 方法 2（本地，看启动它的那个 shell）

```bash
# 如果通过 run-local.sh 启动，在该脚本运行前先 echo，或在另一个终端：
./run-local.sh   # 观察输出 "==> 加载 .env 环境变量"
```

### 方法 3（Spring 权威判断：`/actuator/env`）★ 推荐排查用

这个端点会**列出每个属性的最终值和它的来源（propertySource）**，能一句话回答"到底是哪一层赢的"。

项目当前只暴露了 `health,info,prometheus`（`application.yml` 的 `management.endpoints.web.exposure.include`）。临时加上 `env`：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,env
  endpoint:
    env:
      show-values: always   # Spring Boot 3 默认是 never，不设这行值会显示成 ******
```

然后：

```bash
curl -s localhost:8123/api/actuator/env | python3 -m json.tool | grep -A3 LLM_CHAT_MODEL
```

`propertySources` 里会显示来源名，例如：

- `systemEnvironment` → 说明是**环境变量**赢的（`.env` 生效）
- `applicationConfig: [classpath:/application.yml]` → 说明是 **yml 默认值**赢的（`.env` 没生效）

> ⚠️ 排查完记得把 `env` 从 `include` 里去掉，它会暴露包含 API Key 的配置。

### 方法 4（业务侧确认：看响应里的 served model）

DeepSeek 响应体的 `model` 字段是**实际服务的模型**。注意旧名会被静默改写（请求 `deepseek-chat` 会返回 `deepseek-flash`），所以这个字段能验证"最终到底用了什么"。

## 6. 让 IDE 也能读 `.env` 的两种办法

### 办法 1：装 EnvFile 插件（IntelliJ）

Run/Debug Configurations → 你的 `YuAiCodeMotherApplication` → **EnvFile** 标签 → 添加 `.env`。

### 办法 2：不用插件，直接在运行配置里填环境变量

Run/Debug Configurations → **Environment variables** → 粘贴：

```
LLM_API_KEY=sk-xxx;LLM_BASE_URL=https://api.deepseek.com;LLM_CHAT_MODEL=deepseek-flash
```

缺点是 `.env` 改了要手动同步。

### 办法 3：干脆统一用 `./run-local.sh`

最省心，配置来源唯一。

## 7. 推荐做法

**把 `.env` 当作唯一事实来源（Single Source of Truth）：**

1. **真实值只写 `.env`**（已被 `.gitignore` 忽略，不进版本库）。
2. **`.env.example` 作为模板**随仓库走，字段保持一致。
3. **`application.yml` 里的默认值只作为"占位兜底"**，保证不配 `.env` 也能跑起来。
4. **`docker-compose.yml` 的 `environment:` 必须覆盖 `.env` 里所有需要进容器的变量**。
5. 本地开发**统一用 `./run-local.sh`**，这样本地与 Docker 走的是同一份 `.env`，不会出现"本地能用、容器里不行"。

**新增一个环境变量时的完整清单（三处都要改）：**

- [ ] `.env`（真实值）
- [ ] `.env.example`（模板值）
- [ ] `docker-compose.yml` 的 `environment:`（否则进不了容器）
- [ ] `application.yml` 的 `${VAR:默认值}` 占位（否则 IDE 启动会报错/取不到）

## 8. 附：本次改模型名涉及的位置速查

以 `LLM_CHAT_MODEL` / `LLM_STREAMING_MODEL` / `LLM_ROUTING_MODEL` 为例：

| 文件 | 作用 | 影响哪条路径 |
|---|---|---|
| `.env` | 真实值 | `run-local.sh` + Docker |
| `.env.example` | 模板 | 无（仅给新人复制） |
| `docker-compose.yml` | compose 层默认值 | Docker（`.env` 缺该项时） |
| `src/main/resources/application.yml` | Spring 层默认值 | **IDE 启动**（主）+ 所有路径的兜底 |
| `src/main/resources/application-prod-sample.yml` | 模板 | **无**（profile 未激活） |
| `yu-ai-code-mother-microservice/.../application.yml` | 微服务模块 | **无**（该模块不是主构建的一部分，需独立构建） |
