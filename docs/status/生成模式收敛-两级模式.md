# 生成模式收敛：从 4 种到 2 种

> 时间：2026-10-21（Asia/Shanghai）
> 状态：已完成并验证；P4（工具通道 + 热更新）尚未开始

---

## 1. 改动前 → 改动后

| | 改动前 | 改动后 |
|---|---|---|
| 模式数量 | 4 种：`html` / `multi_file` / `vue_project` / `fullstack` | **2 种**：`static`（纯前端）/ `fullstack`（带存储） |
| 自动识别 | AI 路由（4 选 1，偏好最简单） | **关键词规则**（二分类），见第 3 节 |
| 纯前端产物 | 原生 HTML 或多文件，静态托管，无容器 | 与全栈同一套 React 模板，跑容器，但 schema 无表、不连库 |
| 预览链路 | 两套（静态托管 / 容器代理） | 两种模式走同一条：容器 + `{code}.pv.localhost:8124` |
| 旧类型应用 | 可继续生成 | 仍可查看，但预览返回 410，提示重新生成 |

## 2. 两种模式的定义

### `static` —— 纯前端项目（无数据存储）

- 同一套 `node-unified` 模板与构建链（React + Vite）
- `schema.json`：`tables` 为空、`auth.enabled=false`
- 运行时**跳过迁移、不连数据库**，`/api/health` 返回 `db:"off"`
- AI 只能写 `client/src/**`，禁止调用 `/api`
- 数据只能放内存或 localStorage

### `fullstack` —— 带存储项目

- 现状一体化应用：`schema.json` 声明表 → 启动自动建表 → MySQL
- 归属隔离、自动 CRUD、JWT 登录全部保留

## 3. 自动识别：为什么不用大模型路由

原实现用 LangChain4j 的结构化输出（方法返回枚举）做路由。实测：

- 请求正常发出，**响应 body 只有一个 `{`**，`JsonEOFException` → 每次创建应用都白调一次模型
- 然后静默兜底到某个固定类型 → **所有应用都被判成同一种**
- 也就是说，"AI 智能路由"实际上从未生效过，只是没人发现

改为 `AppModeRouter`（规则路由）：

```
命中以下任一关键词 → FULLSTACK：
记账 账本 台账 账单 开销 收支 流水 记录 历史 待办 todo 清单 任务管理 计划 打卡 习惯
留言 评论 博客 文章 笔记 日记 收藏 点赞 库存 订单 客户 crm 会员 预约 工单 报销 审批
保存 持久化 数据库 后台管理 管理系统 增删改查 统计 报表 登录 注册 账号 用户系统 多用户 权限
否则 → STATIC
```

好处：零延迟、零成本、可解释、可单测；坏处：遇到没覆盖的表述会保守判成纯前端（成本更低的那一侧）。

创建应用时也可以手动指定模式（前端下拉），手动指定优先。

## 6. 已知限制

| 限制 | 说明 |
|---|---|
| 旧类型应用不可预览 | 预览返回 410，需重新生成；旧类型仍能在列表里看到 |
| STATIC 也起容器 | 仍会创建容器（约 150MB）并建一个空数据库；后续可改为按类型跳建库 |
| 关键词路由的边界 | 表述里没有存储类词汇时会判成纯前端；用户可手动选模式 |
| 部署（P5 未完成） | 两种模式的部署仍走旧的静态复制逻辑，发布后不可运行 |
| 遗留测试应用 | 调试过程中创建了十多个测试应用与容器，`scripts/reset-sandbox.sh` 可清容器 |
