## 9. 收敛建议：把 4 份文档压成 1 条主线

**问题**：Grafana §5.2/§6.3、任务监管端 §4、DeepSeek §D、AI 管理端 §4/§5.2 对同一件事给了**三套不一致的表结构与币种**——

| 文档 | 建模思路 | 表名 | 币种/列名 |
|---|---|---|---|
| Grafana §5.2 | **单表**：轨迹与用量同行（`call_type`/`tool_name`/`tool_arguments`/`tool_result`/`content` + token/价格） | `ai_call_record` | `cost_usd`、`input_price`/`output_price` |
| 任务监管端 §4.2 | **双表**：轨迹继续用 `chat_history`（加 `taskId`），用量单独一行 | `ai_usage_call` + `ai_model_price` | `costCny`、`cachedHitTokens`/`cachedMissTokens`、`priceId` |
| DeepSeek §D | **三表**：明细 + 任务汇总 + 价格 | `ai_usage_call` + `ai_usage_task` + `ModelPrice` | `cost_cny`、`price_version` |
| AI 管理端 §4 | 在 `gen_task` 上加 `modelConfigId`/`traceId`/`promptTokens`/`completionTokens` | — | 未给币种 |

**冲突点**：
1. **表名与粒度**：`ai_call_record`（轨迹+用量一表）vs `ai_usage_call`（只存用量，轨迹留在 `chat_history`）；
2. **汇总放哪**：`gen_task` 冗余列（Grafana/任务监管端）vs 独立 `ai_usage_task` 表（DeepSeek）；
3. **币种**：Grafana 用 USD，DeepSeek/任务监管端用 CNY，而 DeepSeek 文档自己论证了"人民币为准确认，不要用汇率反推"；
4. **字段命名**：`cached_hit_tokens` / `cachedHitTokens`、`prompt_tokens` / `promptTokens` 混用。

**如果照四份文档各写一遍，一定会返工。**

**建议**：

1. **只认任务监管端为实施单**，把另外三份降级为"依据/引用"；在四份文档头部统一加一行"以任务监管端 §4 为准"。
2. **表结构定一套**（建议）：`chat_history`（+`taskId`）存轨迹、`ai_usage_call` 存用量、`ai_model_price` 存版本化价格、`gen_task` 冗余汇总（token + 费用）——即任务监管端方案；**放弃** Grafana 的 `ai_call_record` 单表（轨迹与用量混在一起，字段膨胀且难演进）和 DeepSeek 的 `ai_usage_task` 汇总表（多一处一致性风险）。**币种统一 CNY**：DeepSeek 文档已论证官方人民币表才是准的，Grafana 的 `cost_usd` 不采纳。
3. **先做 P0-1（0.5 人日）**：改 `error_type` + 去掉用户/应用 label，独立价值最高，且不依赖任何新表。
4. **再做 P0-2/P0-3/P0-4（3.5 人日）**：表 + taskId + 采集计价，做完就有"按任务的 token/费用"。
5. **最后 P0-5（2 人日）**：两个管理页。**不要先做页面**——页面会倒逼表结构返工。
6. **LOWCODE 单独立项**：它改的是"生成什么"，和监管改的是"怎么看"，两条线并行会互相拖。
7. **Langfuse 维持 P2**：先用 0.5 人日上 `langchain4j-micrometer-metrics` 拿 token 基线，再决定是否值得 6 容器。
