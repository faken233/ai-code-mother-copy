# 预览生命周期：容器自动回收

> 时间：2026-10-21（Asia/Shanghai）
> 状态：已完成并验证

---

## 1. 背景

每次点预览都会拉起一个 `app-pv-{appId}` 容器，之前没有任何回收机制，实测累积到 18 个容器。
生成式平台的预览是"临时看效果"，长期占着容器既吃内存也让 `docker ps` 无法阅读。

目标：

1. 用户**离开预览页**一段时间 → 关容器
2. 用户**还在页面上但长时间没有改动** → 关容器，并弹窗说明
3. 用户回来点「恢复预览」→ 容器重新起来，**链接不变**
4. 部署容器（正式上线）不参与回收

---

## 2. 机制

```
前端（预览页可见时）
  └─ 每 30s  POST /api/app/preview/{appId}/heartbeat
        ├─ 记录 lastSeen
        └─ 返回 { state: READY | SLEEPING | IDLE }

后端（每 30s 扫描一次 app_access_route 里 status=READY 的预览路由）
  ├─ 有生成任务在跑        → 跳过（绝不回收）
  ├─ now - lastSeen   > 120s → sleep(appId, "left")    离开页面
  ├─ now - lastModified > 900s → sleep(appId, "idle")  在页面但没改动
  └─ 否则不动

sleep(appId, reason)
  ├─ docker stop + rm 容器（数据在 MySQL/磁盘上，不受影响）
  ├─ 路由 status → STOPPED（**保留 host**，链接不变）
  └─ 清掉内存里的心跳/修改时间

唤醒
  └─ 再点「预览」→ previewApp → 复用同一个 previewCode → 起容器 → 路由恢复 READY
```

关键设计：**休眠只改状态、不删域名**。所以 `http://7hoxw4ch.pv.localhost:8124/` 这个地址在多次休眠/唤醒之间保持不变。

`lastSeen` 为空时用路由的 `updateTime` 兜底：主服务重启后内存状态清空，不会出现"刚启动就把所有容器当成离开"的误杀（仍然按最后一次路由写入时间 + 宽限期判断）。

## 3. 配置

`application.yml`（都可用环境变量覆盖）：

```yaml
preview:
  lifecycle:
    enabled: ${PREVIEW_LIFECYCLE_ENABLED:true}
    scan-interval-ms: ${PREVIEW_REAPER_INTERVAL_MS:30000}
    leave-timeout-seconds: ${PREVIEW_LEAVE_TIMEOUT_SECONDS:120}    # 离开页面 2 分钟
    idle-timeout-seconds: ${PREVIEW_IDLE_TIMEOUT_SECONDS:900}      # 无改动 15 分钟
    heartbeat-seconds: ${PREVIEW_HEARTBEAT_SECONDS:30}
```

调参建议：

- 演示/答辩：`leave=30`、`idle=120`，容器回收更积极
- 日常开发：默认值即可
- 想临时关掉：`PREVIEW_LIFECYCLE_ENABLED=false`

## 5. 验证结果（用短超时实测）

把 `leave=20s / idle=60s / scan=10s` 起服务后：

| 步骤 | 结果 |
|---|---|
| 点预览 | 容器起来，心跳返回 `READY` |
| 不心跳等 40 秒 | 容器数 1 → **0**，日志 `预览已休眠: reason=left` |
| 再发心跳 | 返回 `SLEEPING`（前端据此弹窗） |
| 再点预览 | **地址不变**（`7hoxw4ch.pv.localhost`），容器恢复，页面 200，心跳 `READY` |
| 默认配置起服务 | 心跳返回 `heartbeatSeconds=30 / leave=120 / idle=900` |

顺带清掉 18 个历史容器；回收任务也会把"容器已不存在但路由还是 READY"的脏路由标成 STOPPED。

另外修掉一个数据问题：并发预览会产生**同一应用两条 PREVIEW 路由**（实测出现过一条 READY + 一条 STOPPED、两个域名）。
现在 `findPreview` 按 `update_time` 倒序取最新，写入后清理同应用的其余路由；表上加了 `unique key uk_app_kind (app_id, kind)`，
线上库已去重并建索引。

## 6. 已知限制

| 限制 | 说明 |
|---|---|
| 状态在进程内 | 主服务重启后所有应用的 `lastSeen` 清空，会按路由 `updateTime` + 宽限期重新判断；多实例部署需要换 Redis |
| 心跳依赖前端页面 | 用户直接关浏览器/断网，心跳停止 → 正常按"离开"回收；这是预期行为 |
| 部署容器不参与 | 目前部署还没容器化（P5），P5 之后 `kind=DEPLOY` 的路由不会被本任务扫描 |
| 与 P6 的关系 | 容器重启后宿主端口变化导致 `upstream` 过期的问题仍未处理，那属于 P6 的 reconcile |
| 弹窗只在预览页 | 用户切到别的页面时容器已被回收，回来时先看到 iframe 的 503，心跳随后弹窗 |
