## 2. 路由对账（reconcile）

**问题**：`app_access_route.upstream` 是某次启动时回读的宿主端口；Docker 重启 / 容器重建后随机端口会变，proxy 仍往旧端口转发 → 502。此前只能靠用户再点一次预览自愈。

**实现**：

- `RouteReconcileJob` 每 60s 扫描一遍 `app_access_route`，只处理 `status=READY` 的路由；
- 扫描前先 `docker info` 探活：Docker 短暂不可用时整轮跳过，避免把"查不到容器"误判成"容器已删"；
- 预览：容器不存在 / 已停止 → `sleep()`（路由置 `STOPPED`，host 保留）；容器在跑 → `docker port` 重新回读，端口变了就写回 DB + Redis；
- 部署：只刷新当前 `ACTIVE` 版本的端口，不改状态、不回收（正式上线必须常驻）；
- 正在搭建/生成（`running` / `sandbox_building`）的应用跳过；只是排队中的任务不跳过；
- 宿主机重启后预览容器可能处于 Exited：`ensureContainer` 会先 `docker start` 复用容器，失败才删掉重建（代码在卷里、数据在库里，不会丢）。

配置（`application.yml`）：

```yaml
route.reconcile.enabled: true
route.reconcile.interval-ms: 60000
route.reconcile.initial-delay-ms: 20000
```

**实测**（把 DB + Redis 故意改成错误端口）：

```text
路由上游已刷新: appId=470511054192021504, kind=PREVIEW, host=mpvjg43o.pv.localhost, upstream=http://localhost:60769
部署上游已刷新: appId=470509859939454976, version=5, upstream=http://localhost:62396
路由上游已刷新: appId=470509859939454976, kind=DEPLOY, host=yxlsix.app.localhost, upstream=http://localhost:62396
```

DB、Redis、`app_deploy.upstream` 三处全部恢复；经 proxy 访问首页 200、`/api/health` 返回 `"app":true`。

**容器停止场景**：停掉预览容器后 47s，路由自动变成 `STOPPED`，proxy 返回 503；再调预览接口唤醒，新容器端口 `64263` 自动写回，地址不变且恢复 200。

**宿主机重启场景**：手工 `docker stop`（保留容器）后立即调预览，日志出现
`容器已存在但已停止，尝试启动`，容器恢复 `Up`，端口与地址均不变；若 `docker start`
失败则自动删除重建。

## 3. 应用删除回收

`AppCleanupService#cleanupAfterDelete(appId, codeGenType, deployKey)` 按顺序 best-effort 执行（任一步失败只告警，不阻断删除）：

1. 删预览 + 部署路由（DB + Redis）；额外按 `deployKey` 兜底删一次「只剩 Redis、没有 DB 行」的部署域名；
2. 停/删预览容器 `app-pv-{appId}`；
3. 删所有部署版本容器、镜像、`tmp/code_deploy/{appId}`、`app_deploy` 行；
4. 删所有 `tmp/code_output/{任意类型}_{appId}`（防止改过类型 / 历史写错目录留下垃圾）；
5. 删预览库 `app_{appId}`、生产库 `app_{appId}_prod` 及同名账号；
6. 清内存里的心跳/空闲状态。

`AppServiceImpl.removeById` 在逻辑删除前先抓取 `codeGenType` 与 `deployKey` 快照，删除成功后调用回收。

**实测**（临时应用，人工造资源）：

```text
app 行 isDelete=1
app_access_route 0 行 / app_deploy 0 行
Redis route:p6check*.pv.localhost、route:p6del2.app.localhost 均不存在
app-pv-{appId} 容器已删除
tmp/code_output/static_{appId} 已删除
app_{appId}、app_{appId}_prod 数据库均已删除
```

## 4. 超时任务覆盖 sandbox_building

- `markSandboxBuilding` 改为 SQL：`startTime = IFNULL(startTime, NOW())`，让沙箱搭建阶段也有超时起点；
- `markRunning` 同样用 `IFNULL`，**不重置**起点（否则沙箱耗时可以绕过超时）；
- `updateTimeoutTasks` 的 `WHERE` 改成 `status IN ('running','sandbox_building') AND startTime IS NOT NULL`；
- `getActiveTasksByUser` 也补上 `sandbox_building`，避免搭建阶段用户看不到自己的任务。

**实测**：插入一条 `sandbox_building`、`startTime` 为 20 分钟前的任务，40s 内被定时清理改为 `failed`，错误信息「任务执行超时」。
