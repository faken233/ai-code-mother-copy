# AI 任务监管端：可行性与设计方案

> 需求（重新调研版）：
> 1. 监管端能看到**每个用户任务**的：对话信息 + 工具调用信息（类似智能体轨迹）
> 2. 该任务的 **token 消耗量**
> 3. 该任务的**费用**（一个任务可能含多轮 LLM 调用，费用要**累加**）
>
> 已确认的约束变更：**不再需要全局模型管理**，继续走环境变量硬编码模型名，使用 DeepSeek。
>
> 调研时间：2026-09-11
> 配套深度报告：

> - `docs/research/langfuse-接入调研报告.md`（如后续要上专用平台）

## 0. 三个问题的直接回答

### Q1：现有 Grafana 能满足监管需求吗？

**分两半，答案不同：**

| 要监管的内容 | 现有 Prometheus + Grafana | 原因 |
|---|---|---|
| **单任务的对话 + 工具调用轨迹** | ❌ **不能** | Prometheus 是 metrics TSDB，只存 float64 + 标签集，**没有文本/JSON 载荷字段**，存不下对话内容和工具参数 |
| **单任务的 token / 成本** | ❌ 不能（按任务粒度） | `taskId` 是**无界维度**（只增不减、永不复用），做标签会导致基数爆炸 |
| **全局 token / 成本聚合大盘** | ✅ **能**，这是它的正确位置 | 按模型、场景、日期聚合，维度有界 |

**这不是配置问题，是数据模型鸿沟，没有任何 Grafana 配置技巧能绕过。**

### Q2：DeepSeek 会返回 token 或费用吗？

| 项 | 结论 |
|---|---|
| token 用量 | ✅ **返回**，且流式也返回（无需任何参数） |
| **费用** | ❌ **完全不返回**，文档、schema、实机三方确认无 `cost`/`price` 字段 |
| 余额 | ✅ 有 `GET /user/balance`（返回人民币余额） |
| 历史账单 API | ❌ **没有公开 API**（官网 sitemap 里不存在；社区用的是私有接口，需登录态，不可依赖） |

→ **费用必须自己按 token × 单价计算**，价格表要自己维护。

### Q3：那应该怎么做？

**推荐：任务级明细落 MySQL + 管理端展示；Prometheus/Grafana 只做聚合大盘。**

**而且——这个需求的真实工作量比预想小得多**：调研发现**轨迹数据其实已经在往数据库写了**（见 §4），缺的只是「taskId 关联 + token 采集 + 成本计算 + 展示页」。

## 1. 为什么 Grafana 做不了轨迹：需求 → 数据形态映射

先把问题说清楚。三类需求的数据形态完全不同：

| 需求 | 数据形态 | 维度基数 | Prometheus 合适吗 |
|---|---|---|---|
| 对话内容（多轮） | 文本、事件、有序 | 每任务 N 条 | ❌ 无文本载荷字段 |
| 工具调用（名称/参数/结果/顺序） | 文本、事件、有序 | 每任务 M 条 | ❌ 同上 |
| token 消耗（**单任务**） | 数值 | **taskId 无界** | ❌ 基数爆炸 |
| token/成本（**聚合**） | 数值 | model/scene/date 有界 | ✅ 正是它的用途 |

**关键区别**：`user_id` 的序列数 ∝ 用户总数（**有界**），而 `task_id` 的序列数 ∝ **历史任务累计数（只增不减，永不复用）**。

### 量化（来自 Grafana 调研报告 §5.1）

按 **1000 任务/天 × 5 次 LLM 调用 × 15 天保留**估算：

- 窗口内 ≈ **15,000 个 taskId**
- 仅现有 4 个指标合计 → **≈ 9 万 ~ 30 万条序列**

而 Prometheus 官方在 [Instrumentation 最佳实践](https://prometheus.io/docs/practices/instrumentation/) 中明确：单指标基数建议 **< 10**，**超过 100 就应该"把分析从监控系统移到通用处理系统"**。

> 作为对照：现有代码 `AiModelMetricsCollector` 已经用 `user_id` + `app_id` 作标签（有界但不小），如果再加 `task_id`，就是在这个基础上再乘一个无界因子。

### 其余三条路也都堵着或代价高

| 方案 | 能否满足 | 代价 |
|---|---|---|
| **Prometheus exemplars** | ❌ 不能按 taskId 检索 | 固定大小内存环形缓冲，定位只是"从大盘点进某条 trace"的**反向导航**；OpenMetrics 规定标签≤128 字符 |
| **Loki**（日志） | ⚠️ 勉强可以 | `task_id` 必须走 **structured metadata**（官方明说 trace ID / order ID 这类"ephemeral values"不要做 label）；**没有对话化 UI**，只是一行行日志 |
| **Tempo**（trace 树） | ✅ 树形最贴切 | 需要**对象存储** + 新组件；且 OTel 语义约定里工具入参/返回值（`gen_ai.tool.call.arguments`/`result`）是 **Opt-In**，默认不采集，要自己开 |
| **Grafana Cloud AI Observability** | ✅ 但拿不到 | 官方 LLM 看板（OpenLIT）安装路径写明 "In your **Grafana Cloud** stack"，**OSS 自建栈用不了**，且当前是 public preview |

> ⭐ 一个权威背书：OTel 官方明确「内容默认不采集」，并**推荐生产环境"把正文外置存储、span 上只留引用"**——这正是本方案推荐的 MySQL 路线。

## 2. 关键发现：轨迹数据其实已经在落库了

这是本次调研最有价值的代码级发现。逐条核对现有实现：

| 数据 | 现状 | 位置 |
|---|---|---|
| 用户消息 | ✅ **已持久化** | `chat_history`，`messageType=user` |
| AI 回复 | ✅ **已持久化** | `chat_history`，`messageType=ai` |
| **工具调用** | ✅ **已持久化**（含 `name` / `displayName` / `summary` / `result` / `status`） | `chat_history`，`messageType=tool_call`，由 `GenTaskExecutor.persistToolCall()`（`:338`）写入 |
| 任务正文 | ✅ 已持久化 | `gen_task.generatedContent` |
| 思考内容 | ⚠️ 仅日志，不落库 | `AiCodeGeneratorFacade:130` |
| **taskId 关联** | ❌ **缺失** | `chat_history` 只有 `appId`，无法把工具调用归属到具体任务 |
| **token 用量** | ❌ **被丢弃** | `AiCodeGeneratorFacade:141` 的 `onCompleteResponse(ChatResponse response)` 拿到响应后直接 `sink.complete()`，**usage 未采集** |
| **费用** | ❌ 完全没有 | — |

**结论**：轨迹的"原料"已经在库里了，只是**按 appId 组织、而非按 taskId**。这个需求的真实工作量集中在三件事：

1. 给轨迹加 **taskId 关联**（小）
2. 采集 **token**（小，钩子现成）
3. 计算 **成本**（中，需要价格表）

## 3. DeepSeek 侧：能拿到什么、拿不到什么

> 以下均为 `docs/research/DeepSeek-用量与费用调研报告.md` 的结论，**带「实测」的是用真实 API Key 跑出来的**。

### 3.1 ⚠️ 最紧急：模型名已退役（与监管无关，但会直接影响生产）

官方 changelog 声明 `deepseek-chat` / `deepseek-reasoner` 已于 **2026-07-24 15:59 UTC 退役**。

**实测结果（重要）**：这两个旧名字**目前仍能调用，但被静默路由到 `deepseek-flash`**，响应体的 `model` 字段返回 `deepseek-flash`。传一个真正不存在的名字会得到官方 400：

```
"The supported API model names are deepseek-flash, deepseek-v4-pro, but you passed deepseek-v3."
```

**两个直接后果：**

1. **计价必须用响应里的 `model`（served model），不能用请求参数**——请求写 `deepseek-chat`、实际按 `deepseek-flash` 计费。
2. 项目里 `application.yml` 的默认值、`application-prod-sample.yml`、微服务 `application.yml` 仍写着 `deepseek-chat` / `deepseek-reasoner`，建议统一改为 `deepseek-flash`。
3. 思考/非思考**不再用模型名区分**，改为请求参数 `thinking.type = enabled|disabled`（默认 enabled）+ `reasoning_effort`。

### 3.2 usage 字段完整结构（实测原样）

```json
"usage": {
  "prompt_tokens": 1295,
  "completion_tokens": 128,
  "total_tokens": 1423,
  "prompt_cache_hit_tokens": 1152,
  "prompt_cache_miss_tokens": 143,
  "prompt_tokens_details": { "cached_tokens": 1152 },
  "completion_tokens_details": { "reasoning_tokens": 27 }
}
```

| 字段 | 说明 |
|---|---|
| `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` | DeepSeek 专有，**命中与未命中单价差 30~50 倍，必须分段计价** |
| `prompt_tokens_details.cached_tokens` | 实测 **== `prompt_cache_hit_tokens`** |
| `completion_tokens_details.reasoning_tokens` | **仅思考模式出现**；非思考模式下该子对象**整个不存在** |
| **`cost` / `price` / `currency`** | ❌ **不存在** |

**关键计费结论**：`reasoning_tokens` **已包含在 `completion_tokens` 内**，按输出价计费。
→ **计费只算 `completion_tokens × 输出价`，不要再加一次 `reasoning_tokens`，否则费用翻倍。**

### 3.3 流式也能拿到 usage（且比 OpenAI 更省事）

**实测：`stream=true` 不需要任何参数就会返回 usage**（与 OpenAI 必须显式 `include_usage` 不同）。`stream_options.include_usage=true` 也支持，但结果完全一致，**没有独立的 usage-only chunk**。

usage 挂在 `data: [DONE]` 前那个带 `finish_reason` 的 chunk 上。

> 项目侧还有一层好消息：LangChain4j 的 `OpenAiStreamingChatModel:161` **已经自动注入** `stream_options.include_usage(true)`，并且会把结果聚合进 `ChatResponse.metadata().tokenUsage()`。所以流式路径天然能拿到 usage。

### 3.4 当前价格（查询日期 2026-09-10，人民币，元/百万 tokens）

| 计费项 | 时段 | `deepseek-flash` | `deepseek-v4-pro` |
|---|---|---|---|
| 输入（缓存**命中**） | 空闲 | 0.02 | 0.15 |
| 输入（缓存**命中**） | 高峰 | 0.04 | 0.30 |
| 输入（缓存**未命中**） | 空闲 | 1 | 4.5 |
| 输入（缓存**未命中**） | 高峰 | 2 | 9.0 |
| 输出 | 空闲 | 4 | 13.5 |
| 输出 | 高峰 | 8 | 27.0 |

**高峰时段**（官方原文）：**北京时间周一至周五 9:00–12:00、14:00–18:00**，其余为空闲；**周末全天空闲**。空闲价 = 高峰价的一半。

> ⚠️ 官方**未说明**跨峰谷边界时按哪个时刻判定（litellm 用"完成时刻"，属非官方规则）。
> ⚠️ 价格变动频繁：2026 年就调了 4 次（4/26、8/16、8/23、9/10），且**没有查询价格的 API**。

### 3.5 LangChain4j 侧的可用性（本机源码核实）

| 项 | 结论 |
|---|---|
| `TokenUsage` 实际类型 | `OpenAiTokenUsage`，可转型拿到 `inputTokensDetails().cachedTokens()` 和 `outputTokensDetails().reasoningTokens()` |
| 缓存字段 | LangChain4j **只解析** OpenAI 标准的 `prompt_tokens_details.cached_tokens`，**不解析** DeepSeek 专有的 `prompt_cache_hit_tokens`。**但实测两者数值相等**，所以等价可用 |
| 流式 usage | ✅ 自动注入 `include_usage`，聚合进 `ChatResponse.metadata().tokenUsage()` |
| 计价用的模型名 | `metadata().modelName()` 取的是**响应**的 `model` 字段 → 可直接用于查价 ✅ |
| 内置成本计算 | ❌ **没有** |

## 4. 推荐方案

### 4.1 总体架构

```
                    ┌──────────────────────────────────────┐
   任务执行 ───────▶│  AiModelMonitorListener (已有钩子)     │
   (多轮/多节点)     │  onResponse: 读 tokenUsage           │
                    │  写 MonitorContext.taskId            │
                    └───────────────┬──────────────────────┘
                                    │
              ┌─────────────────────┴─────────────────────┐
              ▼                                           ▼
   ┌──────────────────────┐                  ┌────────────────────────┐
   │ MySQL（账本 + 轨迹）   │                  │ Prometheus（大盘）      │
   │ ai_usage_call  明细   │                  │ 只有低基数标签：        │
   │ gen_task      汇总    │                  │ model / scene / status │
   │ chat_history  +taskId │                  │ ← 成本趋势、失败率      │
   │ ai_model_price 价格表  │                  └───────────┬────────────┘
   └──────────┬───────────┘                              ▼
              ▼                                    Grafana 大盘
   ┌──────────────────────┐
   │ 管理端（自研页面）      │
   │ 任务列表→点进看轨迹     │
   └──────────────────────┘
```

**一句话**：**明细和账本进 MySQL，聚合指标进 Prometheus，轨迹展示自己做。**

### 4.2 表设计

**(1) 轨迹：给 `chat_history` 加 taskId**

```sql
alter table chat_history add column taskId bigint null comment '所属生成任务ID';
create index idx_taskId on chat_history (taskId);
```

> 改动极小——现有的 `tool_call` 记录结构（`name`/`displayName`/`summary`/`result`/`status`）已经够用了。
> `GenTaskExecutor.persistToolCall()` 和 `addChatMessage()` 调用处补传 `taskId` 即可。

**(2) 用量明细：每次 LLM 调用一行**

```sql
create table if not exists ai_usage_call
(
    id               bigint auto_increment comment 'id' primary key,
```

**(4) 价格表：版本化，带生效时间**

```sql
create table if not exists ai_model_price
(
    id             bigint auto_increment comment 'id' primary key,

    inputHitPrice  decimal(18, 8) not null comment '缓存命中输入价（元/百万 tokens）',

```

> **为什么要版本化**：DeepSeek 2026 年调价 4 次。任务记账时必须**固化当时的单价快照**（`priceId`），否则历史账目会随价格表更新而"漂移"，无法对账。

### 4.3 采集：扩展已有的 `AiModelMonitorListener`

**不用新写埋点**——现有的 `AiModelMonitorListener` 就是 `ChatModelListener`，且**每次 LLM 调用都会触发 `onResponse`**，天然覆盖：

- 一个任务内的**多轮**工具调用循环（`maxSequentialToolsInvocations(20)`，每次循环都是一次独立的模型调用）
- LangGraph4j 工作流的**多个节点**
- 重试

改造点：

| 文件 | 改动 |
|---|---|
| `monitor/MonitorContext.java` | 加 `taskId` / `scene` 字段 |
| `task/GenTaskExecutor.java:218` | 设置 context 时补 `taskId`（`executeTask` 的入参，现成的） |
| `monitor/AiModelMonitorListener.java` | `onResponse` 里：解析 `OpenAiTokenUsage` → 算 hit/miss → 查价 → 写 `ai_usage_call` + 累加 `gen_task` |
| `monitor/AiModelMetricsCollector.java` | 只保留**低基数**标签（model/scene/status），**去掉 `user_id`/`app_id`/`error_message`**（见 §6） |

**⚠️ 三个必须处理的坑：**

1. **ThreadLocal 跨线程会丢上下文**
   `MonitorContextHolder` 是纯 `ThreadLocal`，而代码里已经有 `publishOn(Schedulers.boundedElastic())`，LangGraph4j 节点更是跑在自己的执行器里。
   现有实现靠"在 `onRequest` 把 context 塞进 `requestContext.attributes()`、在 `onResponse` 再取回来"绕过了响应侧，但**前提是 `onRequest` 触发时 ThreadLocal 里有值**——这个前提在跨线程场景下不成立。
   **对策**：在 LangGraph4j 节点包装层显式 `setContext`；或改用 Reactor Context 传播；上线前用真实并发任务实测归集是否完整。

2. **重试会重复计费，必须如实记录**
   `GenTaskExecutor:236` 有 `retryWhen(Retry.backoff(...))`。重试是**真实的重复消费**，不能忽略也不能去重——用 `retryNo` 字段如实记录，汇总时累加。

3. **routing 场景用的是 DashScope `qwen-turbo`，不能用 DeepSeek 价目表**
   `LLM_ROUTING_BASE_URL` 指向阿里云 DashScope。查不到价的模型**记 `costCny = null` 并打标**，不要用 DeepSeek 价格硬算，否则账目失真。

### 4.4 成本计算

**公式：**

```
costCny = Σ_call [ (cachedHitTokens  × inputHitPrice
                  + cachedMissTokens × inputMissPrice
                  + completionTokens × outputPrice) / 1_000_000 ]
其中 cachedMissTokens = promptTokens − cachedHitTokens
```

**Java 实现要点：**

```java
// 1) 必须用 BigDecimal，不能用 double（金额精度）
// 2) 中间计算 scale 留 8 位，最终汇总再 HALF_UP 到 4 位或分
// 3) 单价按 servedModel + 峰谷取；峰谷按请求时刻判定
private static final BigDecimal MILLION = new BigDecimal("1000000");

public BigDecimal calcCost(long hit, long miss, long out, AiModelPrice price) {
    return new BigDecimal(hit).multiply(price.getInputHitPrice())
            .add(new BigDecimal(miss).multiply(price.getInputMissPrice()))
            .add(new BigDecimal(out).multiply(price.getOutputPrice()))
            .divide(MILLION, 8, RoundingMode.HALF_UP);
}

/** 高峰：北京时间周一至周五 9:00-12:00、14:00-18:00 */
public boolean isPeak(ZonedDateTime beijingTime) {
    DayOfWeek dow = beijingTime.getDayOfWeek();
    if (dow == DayOfWeek.SATURDAY || dow == DayOfWeek.SUNDAY) return false;
    LocalTime t = beijingTime.toLocalTime();
    return (!t.isBefore(LocalTime.of(9, 0)) && t.isBefore(LocalTime.of(12, 0)))
        || (!t.isBefore(LocalTime.of(14, 0)) && t.isBefore(LocalTime.of(18, 0)));
}
```

**成本量级参考**（`deepseek-flash`，空闲时段）：

| 场景 | 输入 | 输出 | 费用 |
|---|---|---|---|
| 单次小任务 | 50K（其中 40K 命中缓存） | 8K | 40K×0.02/M + 10K×1/M + 8K×4/M ≈ **0.04 元** |
| 多轮工具调用任务（10 轮） | 500K（多数命中） | 60K | ≈ **0.3~0.5 元** |

> 缓存命中率对成本影响极大（命中价是未命中的 1/50）。因为每轮都会带上系统提示词 + 历史，**实际命中率通常很高**，所以**必须分段计价**，否则会把成本高估几十倍。

### 4.5 管理端页面

复用现有 admin 体系（`@AuthCheck(mustRole = ADMIN_ROLE)` + `pages/admin/*` + `openapi2ts`）：

| 路由 | 页面 | 内容 |
|---|---|---|
| `/admin/taskManage` | **任务监管**（核心） | 列表：任务ID / 用户 / 应用 / 类型 / 状态 / **LLM 轮次** / **token（输入·命中·输出）** / **费用** / 耗时；搜索 + 分页 |
| `/admin/taskManage/:taskId` | **任务轨迹详情**（核心） | 按时间顺序渲染该任务的完整轨迹：用户消息 → 思考块 → 工具调用卡片（名称/参数摘要/结果）→ AI 回复；顶部汇总卡片显示 token 与费用；下方可展开"每次 LLM 调用明细" |

## 5. Grafana 在新方案中的正确位置

**不要试图让 Grafana 展示轨迹，但保留它做聚合大盘**——这正是它的强项：

| Grafana 适合看 | 说明 |
|---|---|
| 每日/每小时费用曲线 | 需新增低基数指标 `ai_model_cost_cny_total{model,scene}` |
| 按模型的 token 消耗趋势 | 现有 `ai_model_tokens_total` 改标签后即可 |
| 失败率、响应时长 | 现有 `ai_model_requests_total` / `ai_model_response_duration_seconds` |
| 从大盘跳进具体 trace | 用 **exemplars** 挂 traceId/任务链接（反向导航，不能按 taskId 检索） |

**一个重要提醒**：Grafana 的"费用"和 MySQL 的"账本"**必须同源**——指标从同一份 `ai_usage_call` 明细聚合出来，避免两处数字对不上。

> 如果将来确实想要"树形 trace 视图"而懒得自研，再考虑 Langfuse（6 容器运维成本）或 Phoenix，详见 `docs/research/Grafana技术栈-AI任务级轨迹监管-技术调研报告.md` §4。**但就"看轨迹 + token + 成本"这三个诉求而言，MySQL 自研路径边际成本最低**——库、ORM、管理端、鉴权、消息渲染都已经有了。

## 6. ⚠️ 顺带发现的现网隐患（建议独立于本需求尽快修）

Grafana 调研过程中发现的**代码级证据**，我已逐条核对确认：

**`error_message` 被当作 Prometheus 标签使用，会导致无界基数。**

证据链：

1. `monitor/AiModelMonitorListener.java:70` — 取原始异常消息：
   ```java
   String errorMessage = errorContext.error().getMessage();
   aiModelMetricsCollector.recordError(userId, appId, modelName, errorMessage);
   ```
2. `monitor/AiModelMetricsCollector.java:59` — **原样用作 label**：
   ```java
   .tag("error_message", errorMessage)
   ```
3. `grafana/ai_model_grafana_config.json:1126` — 现有面板直接聚合它：
   ```json
   "expr": "sum by (error_message) (increase(ai_model_errors_total[$__range]))"
   ```

**后果**：异常消息通常含变量内容（URL、ID、上游返回体），**每条不同的错误消息都会新建一个序列**，且 `errorCountersCache`（`ConcurrentHashMap`）在应用堆内也**无界增长**。

**修复建议**：改为低基数 `error_type`（`timeout` / `auth_failed` / `rate_limited` / `upstream_5xx` / `unknown`），原始异常消息落日志或 `ai_usage_call.errorMessage` 字段。同时建议**移除 `user_id` / `app_id` 标签**（用户数增长即无界），需要按用户分析时走 MySQL。
