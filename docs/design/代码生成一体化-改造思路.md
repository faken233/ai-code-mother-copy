> 用途：新会话开工前的上下文包。读完这一份就能直接动手，不必再翻其它调研报告。
> 权威源文档：`docs/design/LOWCODE-APP-DESIGN.md`（269 行，v1.0，2026-08-31）——**一体化方案只在这一份里**，重点 §1–§7、§10。
> 现状核对：`docs/status/设计文档-落地对照.md`（A 域 18 项里 0 项落地，代码改动量为 0）。
> 当前代码仍生成 **Vue3 + Spring Boot 前后端分离工程**，本文是它的替代方案。

---

## 0. 一句话

把"生成前后端分离工程"改成"生成**一个一体化应用**"：

> 一个应用 = 一个服务 = 一个端口（Node18 + Express + React + MySQL-only）；前端构建产物由 Express 托管，`/api/**` 同源；访问走 `accessCode` 短链 + 独立代理服务，**预览链接即部署链接**。

## 2. 目标形态

```
用户业务描述
  → 主服务（Spring Boot 8123）：任务队列 → AI 生成 → 写沙箱
  → 沙箱容器 code-sandbox-{appId}（单端口）：
        node server.js  = Express 托管 public/dist + /api/** + SPA 兜底
        mysql2 → 独立库 app_{appId}
  → 主服务写路由表（PREVIEW/DEPLOY，accessCode）
  → 独立代理 proxy（WebFlux，:8180）：
        /{accessCode}/**  →  剥前缀流式反代到沙箱单端口
```

五个改造面：**生成模板 / 沙箱运行 / 访问路由 / 主服务接口 / 生命周期**。

## 3. 改造面 1：生成模板（最优先，决定后面一切）

### 3.1 目标工程结构（§4.1）

```
my-app/
├── package.json          # express / mysql2 / jsonwebtoken / bcryptjs
├── server.js             # 静态托管 public/dist + /api/** + 启动建表
├── config.js             # 读 DB_HOST/DB_PORT/APP_DB/DB_USER/DB_PASS/JWT_SECRET
├── db.js                 # mysql2/promise 连接池 + 轻量 CRUD 辅助
├── auth.js               # JWT 中间件 + bcryptjs
├── routes/api.js         # 自动暴露 /api/{table} 的 CRUD
├── schema.sql            # CREATE TABLE IF NOT EXISTS（AI 按业务生成）
└── public/dist/          # React(Vite) 构建产物
```

### 3.2 必须写进 prompt 的硬约束（§4.3/§4.4）

- **一个端口**：`app.use(express.static('public/dist'))` + `app.use('/api', ...)` + SPA 兜底（非 `/api` 回 `index.html`）
- **仅 MySQL**：禁止 `data-redis` / Redisson / 任何缓存中间件；鉴权 JWT 无状态，限流用内存或 DB 计数
- **启动即建表**：`schema.sql` + `IF NOT EXISTS`，无需手工初始化
- **自动 CRUD + 代码内授权**（替代 RLS）：
  - `GET/POST/PUT/DELETE /api/{table}`，表名/字段名/排序字段**白名单**防注入
  - 所有归属查询强制 `WHERE user_id = ?`；`POST` 自动写 `user_id`
  - 涉及私有数据时自动生成 `users` 表 + 注册/登录 + `authRequired` 中间件
- **前端相对路径**：`base: './'` + hash 路由 + `baseURL: './api'`；**禁止**出现 appId / 端口 / 隔离库名
- **构建校验**：前端 `npm run build` 出 `public/dist`；后端 `node -c server.js` + `/api/health` 探活（不再 `mvn package`）

### 3.3 连带改动

- `BuildProjectTool`：scope 判断从 `frontend/`/`backend/` 改成"有 `package.json` 就是前端构建、有 `server.js` 就做语法检查"；`mvn` 分支移除
- `ProjectPathResolver`：项目根仍是 `fullstack_{appId}`，但内部不再有 backend/frontend 两层 → 下载过滤、预览路径都要跟着改
- `ProjectDownloadServiceImpl`：过滤 `node_modules`/`public/dist`（构建产物），保留 `server.js`/`schema.sql`

**验收**：生成一个 todo 应用 → `npm install && node server.js` 能起 → `/api/health` 200 → 不登录能看列表、登录后只能改自己的数据。

## 4. 改造面 2：沙箱运行（单端口 + 进程属容器）

| 改动 | 内容 |
|---|---|
| `SandboxContainerManager` | 只映射一个宿主端口（`18080 + appId % 1000`）；删掉 backend 端口配置 |
| 新增 `SandboxAppLauncher`（替代 `PreviewService`） | `docker exec -d code-sandbox-{appId} node server.js`，**进程属容器**，主服务重启不丢 |
| 健康探测 | 只探 `http://{sandbox.host}:{hostPort}/api/health`，就绪后写路由表 |
| 环境变量 | `APP_DB` / `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASS` / `JWT_SECRET`；**无 Redis 变量** |
| 镜像 | 不需要改（Node18 已在） |

**为什么必须 `docker exec -d`**：现在的 `previewProcessMap` 是内存态，主服务一重启就丢句柄，预览进程变僵尸——这是设计文档 §1.1 点名的缺陷之一。

**验收**：`docker restart` 主服务后，预览链接仍可访问。

## 5. 改造面 3：访问路由（短链 + 独立代理）

### 5.1 路由表（§6.2）

```sql
create table app_access_route (
  access_code  varchar(16) primary key,
  app_id       bigint not null,
  kind         varchar(8) not null,   -- PREVIEW / DEPLOY
  sandbox_host varchar(64) not null,
  port         int not null,
  status       varchar(16) not null,  -- STARTING / READY / STOPPED
  expire_at    datetime null,
  updated_at   datetime,
  key idx_app_id (app_id)
);
```
- Redis 缓存 `proxy:route:{accessCode}`，TTL 对齐 `expire_at`
- **主服务写、代理只读**

### 5.2 URL 规则（§6.1）

| 请求 | 处理 |
|---|---|
| `/{code}` | 301 → `/{code}/` |
| `/{code}/api/**` | 剥前缀 → 转发沙箱单端口 |
| `/{code}/**` | 剥前缀 → 转发（应用内部做静态 + SPA 兜底） |

### 5.3 代理实现要点（§6.3）

- 独立 Spring Boot **WebFlux** 模块 `proxy/`，`WebClient` 流式转发
- **不能用 `RestTemplate`**：它会把响应 `byte[]` 全缓冲，SSE 直接断流（旧 `PreviewProxyController` 就是这个问题）
- 透传 method/headers/body/query；`READY` 才转发，`STARTING` → 503，code 不存在 → 404
- 代理不读 `code_output` 磁盘、不感知生成逻辑 → 可独立扩容

**验收**：`curl -N` 经代理能持续收到 SSE；两个不同 accessCode 指向不同容器。

## 6. 改造面 4：主服务接口

| 位置 | 改动 |
|---|---|
| `AppController.previewApp` | 返回 `{proxy-host}/{accessCode}/`；先写 PREVIEW 路由并拉起应用 |
| `AppServiceImpl.deployApp` | 返回 `{proxy-host}/{deployKey}/`；写 DEPLOY 路由（无 TTL）并删 PREVIEW（原子） |
| `PreviewProxyController` | **下线**（生成项目不再经主服务代理） |
| `StaticResourceController` | 保留：纯静态类型（HTML/MULTI_FILE/VUE）仍走它 |
| 前端 `AppChatPage.vue:803-822` | **必须改**：现在它无视后端返回值、自己拼 `origin + /api/preview/{appId}/`（为了绕开 deploy-host 80 端口 bug）。接代理后要改成用 `res.data.data` |
| 配置 | 新增 `code.proxy-host`（生成项目公开地址），与平台 UI 的 `code.deploy-host` 解耦 |

**验收**：同一条链接先预览、部署后直接变线上站，不闪断。

## 7. 改造面 5：生命周期

- 预览：PREVIEW 路由 TTL 24h；到期/应用删除 → `stopContainer` + 删路由
- 部署：DEPLOY 无 TTL，容器 `--restart unless-stopped`
- 容器打 label（`app.id`、`kind`），定时 reconcile：任务结束/超时/孤儿容器 → 回收
- 补一个现成漏洞：超时回收 SQL 只扫 `status='running'`，`sandbox_building` 永远不会超时

**验收**：连续跑 20 个应用后，`docker ps` 数量收敛，不无限增长。

## 8. 分期：先竖切一条，再铺开

> 设计文档 §10 给了 5 期。建议在它前面加一个 **Phase 0 竖切**，用最小代价验证"这条路能通"，再按原分期铺开。

| 阶段 | 内容 | 出口 |
|---|---|---|
| **Phase 0（1–2 天）** | prompt 只改成"单端口 Node 最小应用"（先不做登录/自动 CRUD）；沙箱单端口；用**固定 accessCode + 手写一条路由**（proxy 服务先不做，用 nginx 或主服务临时转发） | 生成 → 预览 跑通一次 |
| Phase 1 | 生成模板补全：schema 自动建表 + 自动 CRUD + 代码内授权 + JWT | 带登录的 CRUD 应用可跑 |
| Phase 2 | `SandboxAppLauncher` + 正式路由表 + `previewApp/deployApp` 写路由 | 重启主服务预览不断 |
| Phase 3 | `proxy/` 独立服务 + `docker-compose` 加 proxy | SSE 流式透传正常 |
| Phase 4 | 主服务接口切短链 + 下线 `PreviewProxyController` + 改前端 | 预览链接 = 部署链接 |
| Phase 5 | 生命周期：TTL、restart、reconcile、容器 label | 容器数收敛 |

## 9. 关键决策与代价（别在实现时反复摇摆）

| 决策 | 结论 | 代价 |
|---|---|---|
| 一体化单端口 vs 前后端分离 | 一体化 | 放弃 Java 生态与前后端独立扩缩容 |
| Node/Express vs Spring Boot | Node/Express | 类型安全弱、生成能力上限低，但 LLM 出错率低、无 Maven 冷启动 |
| 仅 MySQL vs 引入 Redis | 仅 MySQL | 限流/会话要自己写，不能直接用 Redisson |
| 薄数据层 + 代码内授权 vs Supabase RLS | 薄数据层 | 每张表都要生成归属逻辑，AI 漏写就是越权 |
| 独立 proxy vs 主服务代理 | 独立 proxy | 多一个部署单元、多一张路由表 |
| accessCode 复用 deployKey | 复用 | 部署覆盖预览时需原子切换 |

## 10. 风险与未决问题（开工前先认领）

1. **生成稳定性**：Express/React 产出需要 3–5 次固定 prompt 回归，统计一次通过率。
2. **安全不能只靠 prompt**：`authRequired` + 归属过滤必须做成**模板级硬约束**（prompt + 构建后静态检查双保险），只写一句"请校验归属"AI 一定会漏。
3. **自动 CRUD 注入面**：表名、字段名、排序字段全部白名单；`ORDER BY` 禁止拼接原始字符串。
4. **schema 演进**：`CREATE TABLE IF NOT EXISTS` 无法应对字段变更，低代码迭代必然遇到 → 需预留 migration（哪怕是最简的版本号 + ALTER 脚本）。
5. **端口取模冲突**：`appId % 1000` 会在 1000 个应用后撞车 → 需端口占用表或动态分配。
6. **单机 docker CLI 无法水平扩展**：多副本时路由表该指向哪台？短期接受单机，长期迁 K8s Job 或拆独立 sandbox 服务。
7. **旧数据兼容**：已生成的 `fullstack_{appId}`（Vue+SB）要不要并存/迁移，需明确。
8. **代理细节**：SSE、大响应、超时、`Content-Length`/`Transfer-Encoding`、cookie 域。
